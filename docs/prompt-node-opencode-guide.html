How the Prompt node and Text node work

The Prompt node (src/PromptNode.tsx) holds one or more prompt variants. Any text wrapped in {curly braces} inside the prompt becomes a template variable — and each variable automatically gets its own input handle on the left edge of the node. The Text node (src/TextFieldsNode.tsx) is a list of editable strings; connect it to a variable's handle to supply values.

Try it: edit the Text-node items above or switch prompt variants. The filled preview updates live, exactly like ChainForge's TemplateHighlightTextarea highlighting ({var} in orange = variable, green = filled value).
Special variable {system_prompt}: if a template variable named system_prompt is present (e.g. fed by a Text node), its value overrides the system_message defined in the model settings dialogue for that execution. Each Cartesian-product cell can thus carry its own system prompt — perfect for A/B-testing personas or prompt-injection guardrails side-by-side. When absent, the settings-defined system message applies. The variable still gets its own input handle, like any other.

The mechanics, step by step

Prompt node

  • Template parsing: on every edit, the node re-parses the prompt text for {varnames} and unions them into templateVars.
  • Handles appear/disappear automatically — one input handle per variable. Missing connections block the run ("Missing inputs to one or more template variables").
  • Variants: the ＋ Add prompt variant button adds a sibling prompt. Each variant is an independent prompt; promptText is stored as an array.
  • Execution: before querying, pullInputData() resolves every variable. When multiple variants exist, the node packs all of them into a synthetic variable (var_for_prompt_templates) and treats the template as {prompt}.
  • Special variable {system_prompt}: parsed like any template var, but instead of being interpolated into the prompt body, its connected value overrides the settings-defined system_message (per execution, per row). Combined with the cartesian product, every response row can run under a different system prompt.

Text node

  • A simple list of named string fields. Its output is a list — one value per field row.
  • Each row can also carry a label; downstream, a companion <var> [label] key travels with the value for display in the response table.
  • Connected to a prompt variable, the prompt node runs once per row — this is ChainForge's batching primitive (the "N items in, N responses out" pattern).
  • Other feeders work the same way: File node rows, Inspect/response columns, even prompt variants from an upstream prompt node.

How multiple model providers are supported

Providers are pluggable. The front-end keeps a registry of settings schemas; the back-end keeps a registry of callables. Adding a provider means dropping in a small Python script — no core changes.

Front-end registry

// src/ModelSettingSchemas.tsx
export const ModelSettings = {
  "gpt-3.5-turbo": ChatGPTSettings,
  "claude-v1":     ClaudeSettings,
  "gemini-2.5":    Gemini25Settings,
  "openrouter":    OpenRouterSettings,
  "opencode-zen":  OpenCodeZenSettings, // ← new
  ...
};

Each entry is a JSON schema + UI schema pair handed to react-jsonschema-form inside the settings modal (ModelSettingsModal.tsx). Saved form data is post-processed into kwargs for the Python call.

Back-end provider protocol

# chainforge/providers/protocol.py
@provider(name="OpenCode Zen",
          emoji="⛏",
          category="model",
          models=ZEN_MODELS,
          rate_limit=60,
          settings_schema=OPENCODE_SETTINGS_SCHEMA)
def OpenCodeZenCompletion(
    prompt: str,
    model: str | None = None,
    chat_history: list | None = None,
    temperature: float = 0.7,
    max_tokens: int = 4096,
    **kwargs) -> str: ...

The ProviderRegistry decorator (chainforge/examples/custom_provider_opencode.py) advertises the provider, its model list, and the settings schema the UI should render.

What happens with multiple prompts attached to a Prompt node?

"Multiple prompts" can enter a Prompt node two ways — and both fan out into a Cartesian product of executions. Configure the scenario below and watch the response grid.

2
3
2
= 12 calls

Resulting response table

Each row is one API call. ChainForge groups them in the response table by prompt, then by model, then by the input item (and its [label]). Order in the grid = iteration order of the loop nest: for prompt → for model → for item.

Case A — Prompt variants inside one Prompt node

  • promptText becomes an array [vA, vB, …].
  • run() packs the variants into a synthetic variable (ensureUniqueName("prompt", …)) so the count-fetcher sees {prompt} with N values.
  • Responses are tagged with <var> [label] so the table can label them “Variant A / B” and compare side-by-side.

Case B — Multiple prompt outputs fed in via an edge

  • An upstream Prompt node's outputs (or a Text node's rows) arrive as a list value for a template var.
  • The variable's handle carries the whole list; the node runs once per list element.
  • Combine with Case A and any selected models → the product multiplies. Chains of 2 prompt nodes × 3 variants × 4 items × 3 models = 72 calls. Watch your rate limits (OpenCode Zen: 60/min in the example provider).

The backbone was replaced with OpenCode Zen (an OpenAI-compatible gateway, https://opencode.ai/zen/v1). These are live, clickable mock variations of the settings dialogue: only the settings the OpenCode provider declares in its settings_schema are exposed; legacy OpenAI-era fields are removed; and every other provider is disabled.

OpenCode Zen model pricing

Pay-as-you-go, per 1M tokens (USD). Source: opencode.ai/docs/zen. These rates back the cost labels shown in the model picker (Mock B) and can power per-row cost estimation in the response table.

Auto-reload: when your balance drops below $5, Zen reloads $20 automatically (configurable, can be disabled).
Monthly limits: workspace-wide and per-member caps, e.g. $20/month. Auto-reload may exceed the cap once triggered.

Notes from the Zen docs

  • Free models (highlighted rows) are free for a limited time while teams collect feedback; Big Pickle and Space Bunny Free are stealth models — Space Bunny's provider follows a zero-retention policy.
  • Jev 1.13 (TypeSafe / System One) is a structured-decision model: it returns values and probabilities, not text, on a dedicated /v1/systemone endpoint.
  • Tiered pricing: GPT models are priced per context tier (≤ / > 272K tokens); Claude Sonnet 4.5 and Grok per ≤ / > 200K; Gemini 3.1 Pro per ≤ / > 200K. The table shows the base (short-context) rate.
  • Deprecated: the GPT 5.x Codex family (except GPT 5.3+) was deprecated July 23, 2026; Claude Opus 4.1 (Aug 5, 2026) and Sonnet 4 (Jun 15, 2026) are retired and not listed.
  • Endpoints vary by family: OpenAI/Grok → /v1/responses, Anthropic/Qwen-Flash → /v1/messages, open-compatible models → /v1/chat/completions. The ChainForge example provider pins /v1/chat/completions; supporting all families properly means routing per-category.
